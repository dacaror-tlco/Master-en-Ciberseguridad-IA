## 5.2 XSS confirmado

Después se probó Cross-Site Scripting. El objetivo era verificar si la aplicación insertaba la entrada sin neutralizar HTML/JavaScript. Se utilizaron alertas distintas en campos diferentes para saber qué campo estaba ejecutando el script.

**Payloads de demostración**

| <script>alert('Hola mundo')</script> <script>alert('Hola mensaje')</script> |
| --- |

Las alertas se ejecutaron. La clase trató el comportamiento como XSS confirmado y observó que al volver a la sección el código seguía disparándose, lo que sugiere persistencia del contenido en la aplicación.

| **Dato** | **Interpretación** |
| --- | --- |
| Entrada reflejada | Justifica probar contextos de inyección. |
| JavaScript ejecutado | Confirma que la salida no está correctamente neutralizada para ese contexto. |
| Alertas diferenciadas | Permiten identificar qué campo concreto dispara el comportamiento. |
| Ejecución al volver a la sección | Compatible con XSS almacenado; la transcripción no conserva la implementación interna que lo almacena. |

| **RIESGO Riesgo**  Una alerta solo demuestra ejecución de JavaScript. El impacto puede aumentar si el contexto permite acciones con la sesión de la víctima, especialmente si la aplicación carece de controles adicionales. |

# 7. Cookies de sesión: HttpOnly y Secure

Tras autenticarse con una cuenta creada para la práctica, se inspeccionó el almacenamiento del navegador. Las flags HttpOnly y Secure aparecían en false. Carlos lo presentó como un problema reportable y lo relacionó con el XSS demostrado minutos antes.

| **Flag** | **Qué debería aportar** | **Riesgo si falta** |
| --- | --- | --- |
| HttpOnly | Impide que JavaScript acceda a la cookie mediante APIs como document.cookie. | Un XSS puede tener más facilidad para leer una cookie de sesión no protegida por esta flag. |
| Secure | Hace que el navegador envíe la cookie únicamente mediante HTTPS. | La cookie puede viajar por HTTP si la aplicación lo permite, exponiéndola a intercepción de red. |

| **AMPLIACIÓN TÉCNICA Ampliación técnica**  Secure no “cifra la cookie” y HttpOnly no evita por sí solo un XSS. Son controles complementarios: Secure restringe el transporte a HTTPS y HttpOnly reduce el acceso desde JavaScript. La explicación se separa aquí para corregir una simplificación verbal de clase. |

# 9. Subida de archivos: repaso y profundización

## 9.1 Ruta pública y nombres predecibles

Antes de llegar al bypass, Carlos hizo que Xarxas observara dónde quedaba almacenado un archivo y cómo aparecía su nombre en la URL. La lección fue que el problema no es únicamente “que exista /uploads/”: el riesgo aumenta si hay directory listing, nombres previsibles o contenido de terceros accesible directamente.

| **ACLARACIÓN TÉCNICA Corrección técnica**  En la explicación oral se usa “SUID” al hablar de renombrar archivos con cadenas aleatorias. Por el contexto, el concepto esperado es un identificador aleatorio/UUID generado por el servidor, no el bit SUID de Unix. |
| --- |

## 9.2 Webshell frente a reverse shell

| **Técnica** | **Cómo funciona en esta práctica** | **Ventaja / limitación** |
| --- | --- | --- |
| Webshell | Se sube un PHP ejecutable y los comandos se lanzan desde la propia web. | No necesita que la víctima inicie una conexión saliente hacia Kali; interfaz menos cómoda. |
| Reverse shell | El archivo ejecutado hace que la víctima conecte de vuelta a un listener del auditor. | Canal interactivo más cómodo, pero depende de conectividad de salida, rutas y controles de red. |

Carlos recomendó pensar primero en una webshell para confirmar ejecución de comandos de forma sencilla y, después, decidir si merece la pena convertir el acceso en una shell interactiva.

## 9.3 Bypass basado en Content-Type y firma GIF

El primer intento con PHP fue rechazado como tipo de archivo no permitido. La petición se interceptó con Burp Suite y se revisó la parte multipart: nombre, Content-Type y contenido. La aplicación confiaba demasiado en valores manipulables por el cliente, por lo que se repitió el bypass usado el viernes.

**Estructura de prueba reconstruida desde el material del laboratorio**

| Content-Disposition: form-data; name="file"; filename="webshell.php" Content-Type: image/gif  GIF8; <?php system($\_GET['cmd']); ?> |
| --- |

La idea era declarar el archivo como image/gif y anteponer una cabecera reconocible de GIF, manteniendo después código PHP. En este laboratorio la técnica permitió alcanzar ejecución. Es un bypass específico de una validación insuficiente; no es una regla universal para cualquier upload.

| **BUENA PRÁCTICA Clasificación correcta**  La vulnerabilidad es la validación/gestión insegura de archivos subidos. La webshell es el artefacto usado; la ejecución de comandos es el impacto. No deben contarse como tres fallos independientes sin explicar la cadena. |

# 10. Repositorio .git expuesto

## 10.1 Por qué .git importa

Después del descanso se volvió a /desarrollo/.git/. Carlos explicó que el problema no depende de que el repositorio remoto sea público o privado: si el directorio .git queda servido por HTTP, sus objetos, refs e historial pueden permitir reconstruir el proyecto.

| **RIESGO Idea central**  Ocultar el índice del directorio no corrige el problema. Aunque el directory listing no se muestre, los objetos siguen siendo recuperables si el servidor web los entrega. |

# 11. Git como fuente histórica de evidencia

La parte nueva respecto al viernes fue profundizar en los commits. El árbol de trabajo descargado representa un estado, pero Git conserva cambios anteriores. Por eso una credencial eliminada del código actual puede seguir accesible en el historial.

**Comandos trabajados**

| git log git log --oneline git show <hash\_del\_commit> ls -la |
| --- |

| **Comando** | **Objetivo** |
| --- | --- |
| git log | Ver historial detallado, autores, fechas y mensajes de commit |
| git log --oneline | Reducir cada commit a una línea para seleccionar hashes con rapidez |
| git show <hash> | Inspeccionar los cambios introducidos o eliminados por un commit |
| ls -la | Confirmar que el repositorio reconstruido conserva el directorio .git |

| **RIESGO Valor ofensivo y defensivo**  Los secretos pueden sobrevivir en commits antiguos. Borrarlos del archivo actual no es suficiente: deben rotarse y, cuando proceda, limpiarse del historial con un proceso controlado. |

# 13. Ruido operativo, logs y SOC

Una pregunta de clase abrió uno de los bloques conceptuales más útiles: ¿GitDumper “hace ruido”? Carlos respondió que sí. Descargar muchos objetos en pocos segundos puede dejar una secuencia evidente de peticiones en logs y ser detectable por controles defensivos.

| **Concepto** | **Lectura de clase** |
| --- | --- |
| Ruido | Cantidad, frecuencia y patrón de acciones que facilitan detectar una actividad. |
| Rate / pausas | Reducir la velocidad puede cambiar la forma en que la actividad aparece en logs, aunque no garantiza pasar desapercibido. |
| ProxyChains / Tor | Se mencionó como posibilidad conceptual para distribuir origen de tráfico; no se ejecutó en la práctica. |
| SOC | Una auditoría puede incluir como objetivo comprobar si el equipo defensivo detecta la actividad. |
| Reglas del cliente | El grado de sigilo depende del alcance, contrato, NDA y reglas de compromiso de la auditoría. |

| **METODOLOGÍA Punto clave**  “Ser más sigiloso” no es un objetivo universal. En una auditoría autorizada puede interesar generar señales visibles para validar detecciones, o todo lo contrario si el cliente ha pedido evaluar la capacidad del SOC. Lo decide el alcance. |

# 17. Riesgos, errores y buenas prácticas

- No asignar “éxito” a una hipótesis solo porque el payload aparece reflejado. {{7\*7}} no produjo 49, así que SSTI no quedó demostrada.
- No presentar la fuerza bruta como realizada: se razonó el método, pero la sesión no documenta credenciales obtenidas por Intruder/Hydra.
- No confundir una cookie sin Secure con una cookie “sin cifrar”: el control afecta a su envío por HTTPS.
- No confundir venv con Docker: ambos aíslan, pero lo hacen en capas y con mecanismos distintos.
- No dar por válido cualquier secreto recuperado de Git. Un dato expuesto requiere rotación, pero el acceso solo se confirma autenticando o demostrando el impacto autorizado.
- No evaluar una técnica solo por si “funciona”. También importan alcance, trazabilidad, ruido, impacto sobre producción y capacidad del SOC para detectarla.
- No usar herramientas de descarga masiva sin entender el patrón de peticiones que generarán y sin respetar las reglas de compromiso.

# 19. Glosario

| **Término** | **Definición** |
| --- | --- |
| SSTI | Inyección en un motor de plantillas del servidor que puede evaluar expresiones controladas por el usuario. |
| XSS | Ejecución de HTML/JavaScript controlado por un atacante en el contexto del navegador de una víctima. |
| Rate limiting | Control que limita frecuencia o cantidad de solicitudes/intententos en una ventana temporal. |
| HttpOnly | Flag de cookie que impide el acceso desde JavaScript de página. |
| Secure | Flag que hace que la cookie se envíe únicamente mediante conexiones HTTPS. |
| Webshell | Script alojado en el servidor que permite ejecutar acciones o comandos mediante peticiones web. |
| Reverse shell | Canal interactivo iniciado desde la máquina víctima hacia un listener del auditor. |
| Directory Listing | Índice navegable de los contenidos de un directorio servido por HTTP. |
| .git | Directorio interno de Git que contiene objetos, referencias, configuración e historial del repositorio. |
| venv | Entorno virtual de Python para aislar dependencias de un proyecto. |
| Commit | Instantánea lógica de cambios registrada en el historial de Git. |
| Ruido operativo | Huella observable que una actividad deja por volumen, frecuencia, patrón o artefactos. |
| SOC | Equipo/función de monitorización y respuesta de seguridad que analiza eventos y alertas. |
